The engine already keeps a bounded tail of everything it does, one bucket per backup set plus one for the deployment, and the dashboard already reads it per set. What is missing is a single place that shows all of it, on every page, with the two lines an operator most needs: what a button they just pressed actually did, and what it refused to do.

It sits in the shell, not on a page. The dock is a sibling of the nav-and-content row inside AppShell, so the content column shrinks rather than being covered: nothing overlays the last row of a table the way a floating panel would. Because it never unmounts, a navigation does not reset it, which is the one thing the per-set strips cannot do today. Three kinds of line, and the prefix says which. A set's own work, the engine's deployment-wide work, and what this browser asked for. The engine's feed already carries that distinction as an event scope, so the prefix is read rather than invented.

And every action names the command that would have done the same thing. The $ lines are copy-pasteable backupd invocations, built from the very request the browser sent, so a new operator learns the CLI by using the UI and a support conversation gets commands instead of a description of which buttons were pressed. The # lines are the point rather than an omission: an action with no command to name is a CLI parity gap, and this makes it visible the first time somebody uses the feature instead of at some later audit. Note the second one. backupd run exists, but it runs a cycle in the operator's own shell rather than asking this engine to run one, so it is not the equivalent of the button and the terminal declines to pretend it is.

Thirty-two pixels, always present. It keeps the newest line and a count of the errors and warnings since it was last opened, because a terminal that collapses to nothing teaches an operator to stop opening it. Collapsed or expanded is remembered per browser, and it is the only piece of this that is: the log itself belongs to the deployment, so two people watching the same NAS see the same lines rather than two private views of one machine.

This is the case the current feed cannot serve at all. GET /api/v1/activity/live builds its reading by walking the configured backup sets, so a deployment with none answers "sets": [] and the deployment-wide bucket behind it is unreachable. That is exactly the moment a new operator is pressing buttons and getting nothing back, so the endpoint has to be able to answer for the deployment itself and not only through a set that does not exist yet.
