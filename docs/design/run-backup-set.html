The label changes with the behaviour. internal/app.Service.RunCycle walks every configured set that is not Disabled and not edit-held; there is no schedule per set and no due-ness anywhere in the engine, so Run all due sets promises a filter that does not exist. Run all enabled sets is what it actually does, and the four rows are what it actually decided.

5 · the other five refusals, in the same place, in the same words

409OPERATION_ALREADY_RUNNING another pass is in flight, so this one was not queued behind it. It is refused rather than queued because backing up what is on disk now is not made more correct by being asked for twice

Every press names its command, and here that is load-bearing rather than decorative: the line the button prints is the one thing an operator can still do when the button itself is refused. backup-manager run is the deployment-wide equivalent and backup-manager fetch --backup-set S/B the per-set one, so neither control has a naming gap. They have a routing gap, which this rule makes visible on day one: neither command routes to the serving engine today, so pasting the echoed line starts a SECOND process against the same journal instead of doing what the button did. Closing that is part of this issue.

Two classes and both have to land in the terminal. A refusal the engine produced (409, and a run stopped mid-pass) can be emitted through obs and arrive in the live feed like any other line. A refusal produced in front of the engine (the 403 gate, CSRF, a dead connection) never reaches that buffer at all, so the client writes it into the same log, marked as coming from the browser rather than from the engine, and never silently drops it.
