Activity, when the request does not come back

Clicking Activity on a real 0.3.2 NAS gives a red banner and a disclosure holding the words "correlation id unavailable", and there is nothing behind it. The failure is not that the page broke. It is that neither end kept a single fact about how, so the same screen would look identical for a dropped connection, a truncated body and a mapper that threw.

Activity · today, on the deployment

nothing to act on
✕
Backup Manager could not complete that request.
Advanced details
correlation id unavailable

Where the sentence comes from. useAsync catches e: unknown and, when it is not a BackupManagerError, replaces it with a fixed sentence and the literal string "unavailable". The exception is never read and never stored. The literal is what forces the empty disclosure open: ErrorState hides Advanced details when a failure carried no correlation id, and a literal defeats that.

The request reached the service and came back, so it may well have been carried out; what failed was reading the reply. Copy the details below into a bug report, then try again.
Advanced details
request GET /api/v1/activity status 200 · 41.2 KB · content-type application/json failed at reading the response body exception SyntaxError: Unexpected end of JSON input correlation cid_9Fq2tZk1 (from the response header) at 2026-09-07 14:02:11 +02:00 build 0.3.2 (a41c0d9)

Every line here is a fact somebody already had and threw away. The request path is the argument to request(). The status, size and content type are on the Response. The exception is the value useAsync catches. The correlation id is the X-Correlation-Id header writeError already sets, read on a 2xx as well as a refusal. Nothing here is a stack trace, so §37 still holds: no frames, no source paths, no internals, just what was asked, what came back and what could not be done with it.

The engine's log, on a refusal

after
2026-09-07T14:02:11Z ERROR api_refused route=GET /api/v1/activity code=INTERNAL cid=cid_9Fq2tZk1 err="read activity: sql: database is locked"

Today this line does not exist. listActivity does writeError(w, 500, "INTERNAL", "failed to list activity") and drops err on the floor. Thirty handlers in apps/common/webhost do exactly that, the handlers struct has no logger to write to, and no request logging is installed on the router. Meanwhile describeFailure already tells operators that "its own log holds the detail, under this correlation id", which is a promise the service currently cannot keep for any of them.

Dashboard · Recent activity, same failure

says nothing at all
no rows

The same fetch, and a worse answer. DashboardPage runs the identical useAsync(() => api.listActivity()) and never reads activity.error; it renders (activity.data ?? []).slice(0, 6). So while the Activity page shows a banner with nothing in it, the dashboard shows an empty panel that looks exactly like a deployment where nothing has happened. Both surfaces have to say the same thing about the same failure.
