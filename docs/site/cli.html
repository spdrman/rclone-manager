Reference

The command line

Everything the web interface does, and several things it does not, are reachable from one binary. Every command except version takes --config, which defaults to /etc/backup-manager/config/config.yaml. That default is a file inside the config directory rather than a file mounted on its own, because #196 made the directory the writable mount, which is what lets an install that has never been configured write its first config.yaml instead of refusing to start. Pass the directory and it resolves config.yaml inside it. Running rbm with no arguments prints the whole table and exits 2.

The name changed in 0.3.3

The command is rbm. It used to be backup-manager, which was a mouthful to type twenty times in an afternoon and did not say which product it belonged to.

0.3.3 is a clean cut, so backup-manager stops resolving: images built from 0.3.3 onwards carry rbm and nothing else. Anything you have already written that names the old command, a cron entry, a docker exec, a hand-written compose file, has to move across when you upgrade. If you are reading an older script or a support thread that says backup-manager, it means the same thing, but it will not run against this release.

Where you will still see the old name

In your own history, and in anything written before 0.3.3. The interface echoes the new name everywhere, including in the clips on the web interface page, and the binary answers to both.

Every action has a command, and says which one

The rule EPIC G and EPIC H were both built under: anything an operator can do in the web interface has an equivalent command, and the interface says which one while the action is taken. Not as a caption written by hand beside a button, which is a second string that goes stale the first time a flag changes, but from the same function that would build the command, so the two cannot disagree.

It shows up in three places. Under a form control, recomputed as you edit it, so changing a retention tier's destination changes the printed command. In the notice a run control leaves behind, which matters most on a refusal, because while the destructive gate is shut that command is the only remaining way to do the thing that was just refused. And in the terminal at the bottom of every page, where the engine's own record of an API action carries the command it was equivalent to.

Where there is no equivalent command yet, the line says so and says why, rather than being quietly absent. POST /api/v1/backup-sets/test-connection prints "no equivalent yet, there is no verb that tests a connection before a set exists", which is a more useful thing to read than nothing.

Credentials never appear on these lines

No flag on this surface takes a secret, which is what lets the interface print its command lines copy-pasteable exactly as shown with nothing starred out. A password on a command line is in every process listing on the host, so the connection details the terminal needs are environment variables and the panel prints them once at the top with the password as a placeholder.

The commands

CommandWhat it does
rbm runperform one processing cycle and exit
rbm daemonrepeat the processing cycle at poll_interval. One engine per deployment: it is refused rather than started if another process is already serving that state database
rbm checkvalidate the configuration and the state database, then exit
rbm statusreport process and backup-set health, exiting non-zero unless every set is healthy
rbm sourceslist configured sources and backup sets
rbm backup-set createcreate a backup set. The connection is proven before anything is written and the create is refused when it cannot be; --no-verify writes it anyway, says nothing was proven, and leaves the set marked unverified. On an instance with no config.yaml yet this writes the first one instead
rbm backup-set patchchange one configured backup set in place; only the flags you pass change. An edit that moves the host, port, user, key, trusted host key or remote path is proven before it is written
rbm backup-set removetake one backup set out of the configuration. Configuration only: the backups it collected stay on storage and stay listed, and creating the set again with the same source and name takes them back
rbm backup-set test-connectionprove one configured source: resolve, connect, check the host key, offer the key, authenticate, list the folder. Six named outcomes and a non-zero exit when any fails. A pass clears the unverified mark a --no-verify write left
rbm backup-set edit-holdtake or release the hold the web editor takes on a set, so a cycle does not start against a set somebody is halfway through changing
rbm artifactslist journal artifacts, optionally filtered by source and backup set; with a full artifact id, print one artifact's detail including the reason recorded for a failed or quarantined one
rbm activitylist recorded lifecycle events, newest first: the same durable transition log the Activity page draws. --follow tails the live feed instead, which needs something serving the deployment
rbm fetchrun one backup set's cycle on demand
rbm retentionpreview retention decisions, with per-run policy overrides. A preview and nothing else
rbm retention applycarry out a previewed plan. The destructive one, behind --acknowledge
rbm reconcilereconcile the journal against what is actually on disk, for every backup set
rbm validatere-check one artifact's durable copy, wherever it is. --content downloads a copy on a storage medium and re-hashes it
rbm catalog rebuildreconstruct a lost or corrupted state database from the sidecar recovery manifests
rbm quarantinerevalidate, retry or reinstate one quarantined artifact
rbm retryput one failed backup back into the pipeline so it is attempted again
rbm unconfiguredlist the backup sets the journal remembers and the configuration no longer declares, and clear one when you mean it
rbm mediumthe storage destinations: list, show, add, edit, remove, default, import-credentials, and test-connection (also spelled preflight). See the storage page
rbm settingsread the deployment's own settings, and settings patch to change them, including binding a retention tier to a destination
rbm restoreask the storage provider to make one archived copy readable again. --acknowledge is required rather than a --force to skip, because a restore is billed and takes hours. Restore execution is a different thing and is out of scope: getting a backup back onto a server is a documented manual procedure
rbm versionreport the binary, Go and embedded rclone versions

The README's copy of this table is checked against the binary's own dispatch table on every run of the repository's gate. The copy above is checked too, though less deeply: docs/site/tools/check-cli-table.mjs reads the same dispatch table and refuses a page that is short a command, carries a command the binary does not have, or writes an invented verb into a code block anywhere on this site. What it cannot check is the right-hand column, because that is prose. So if this table and the README ever disagree about what a command does, the README is right.

Beside a running engine, and without one

Several of these commands behave differently depending on whether something is already serving the deployment, and the difference is not a fallback. One engine per deployment is enforced: a second daemon against the same state database is refused rather than started.

So a command that has an API route takes it when an engine is there, which means the change reaches the running process with no restart and its steps land in the live feed. With nothing serving, the same command calls the same service layer the route is built on, in your terminal. A command whose answer only exists in the memory of a serving process, such as the live feed or an edit hold, is refused outright when nothing is serving, because a fallback there would put a different feed on screen looking exactly like an answer.

Every configuration read and write says which of those two worlds its answer came from, on stderr, on every run.

Reading an exit code

The codes are a published table rather than a convention, so a script can branch on what happened instead of on the sentence it printed. 0 means the command did what it was asked. 1 is an ordinary failure: a configuration that will not load, a cycle that backed nothing up, a set that is not there, a status short of healthy. 2 means nothing ran. 3 means another process is already serving this deployment, so nothing was done.

The row worth reading twice is 2, because it catches something people assume is a success. rbm check -h is a correct command line and a request the binary answered, and it still exits 2: 2 says no command was carried out, and asking for the help is one of the two ways to get there. So is rbm with no arguments. A wrapper that treats 2 as “fine, it printed the help” swallows every real usage error alongside it.

The two worth knowing before you write a cron entry: status exits non-zero unless every backup set is healthy, which makes it the thing to call from a monitor, and check exits non-zero on a configuration or state database that will not load, which makes it the thing to call before a deploy.
